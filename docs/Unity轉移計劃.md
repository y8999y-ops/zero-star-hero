# Unity 轉移計劃（v0.3，2026-11-06）

> 狀態：進行中（階段 1 做完，等使用者試玩確認）。標「待決定」的地方要等使用者選。

## 0. 已決定（2026-11-06 使用者）

- **目的**：上架手機商店、之後自己在 Unity 編輯器裡做、效能。三個都要。
- **網頁版**：搬的期間凍結，只修壞掉的地方；森林場景的 Aseprite 重畫照常進行。
- **輸出平台**：Android、PC（Windows／Steam）。不做 iOS、網頁。
- **分工**：使用者不寫程式，只負責場景與美術的編輯；程式、數值、特效由 Claude 負責。
- **做法**：B＋（見 2b），編輯器工具以「場景擺放」和「美術匯入」為主。

    毒雲的氣層每一欄只畫到畫面上自己那一欄，改成切段同時畫（結果一樣）→ 每格 7.5 ms，那一段 56～60 fps。
    換關的那一格會卡約 0.2 秒（載入新關卡；網頁版是重新載入頁面）。
- 下一步：3c（1-4 王）、3d（世界地圖）。

## 2. 做法（建議 B）

- **A. 不移植，包成 App**：最快，但不是 Unity 專案。使用者已經決定要 Unity，所以不考慮。
- **B. 照原樣搬（建議）**
  - Unity 裡做一張 384×216 的「像素畫布」（一張貼圖），每一格照現在的算法把像素算出來、貼上去、放大顯示。
  - 程式邏輯寫成一般的 C# 類別，只用一個 GameRoot 物件驅動，固定每秒 60 步，跟現在一樣。
  - 好處：
    - 主角、魔物、特效、大招全部保留，畫面跟現在一模一樣。
    - 可以「同一格畫面網頁和 Unity 比對」，搬錯一眼就看得出來。
- **C. 改成 Unity 標準做法**
  - 先把所有圖和特效輸出成圖片，在 Unity 改用圖片物件、Animator、物理系統。
  - 好處：之後在 Unity 編輯器裡比較好調。
  - 壞處：
    - 手感、打擊感全部要重調。
    - 程式畫的變化（換色、骨架動作、形態外觀）會變成大量圖片。
    - 工作量最大。

B 搬完之後，想慢慢把某些部分改成 Unity 標準做法也可以，不衝突。

### 2b. 建議：B＋（因為目的包含「自己在 Unity 裡做」）

- 畫面和手感照 B：像素畫布、程式照算，保證跟現在一樣。
- 但「會想自己調的東西」從程式裡拉出來，變成 Unity 編輯器裡可以直接改的資料（ScriptableObject）：
  - 怪物數值、掉落、經驗。
  - 形態的連段表（傷害、距離、節奏）、技能樹節點、大招數值。
  - 裝備、詞綴、獨特物品、任務、商店、對話台詞。
  - 打擊感參數（停頓、震動、速度）。
- 關卡改成在 Unity 場景裡擺：
  - 地形用 Tilemap 畫。
  - 怪物、機關、寶箱、出口用預製物件拖進場景擺位置。
  - 遊戲執行時再把它們交給像素畫布去畫。
- 一個 Unity 視窗工具，可以在編輯器裡直接預覽形態、怪物、特效的動畫，調完馬上看。
- 這樣畫面不變，但之後加怪、加關、調數值都可以不寫程式。

### 2c. 使用者在 Unity 裡會做的事（分工）

使用者只做場景和美術，程式、數值、特效都由 Claude 負責。所以 Unity 編輯器工具的重點是：

- **擺關卡**：
  - 地形、平台用 Tilemap 畫。
  - 怪物、機關、寶箱、門、出口、裝飾道具從一個面板拖進場景。
  - 場景裡直接看到跟遊戲一樣的像素畫面，不用按播放。
- **換背景**：
  - 每一關選用哪一組背景圖層（back／far／mid／near／fg）。
  - 視差速度、霧、光的顏色用滑桿調。
- **放美術**：
  - Aseprite 存出的 PNG 丟進指定資料夾，自動設成像素圖（不模糊、不壓縮）。
  - 場景、道具馬上能用。
- **城鎮擺設**：NPC、建築、路燈的位置。
- **不需要碰的**：程式、數值表、特效。數值想改的話跟 Claude 說，由 Claude 改。

每個工具做好時附一份圖文操作說明（docs/Unity操作說明.md），先在第 3 階段（關卡）一起做。

## 3. 技術選擇（B 的做法）

| 部分 | 做法 |
|---|---|

## 4. 怎麼確認搬對了（比對測試）

1. **單張圖比對**
   - 主角、各形態、魔物、圖示、特效的每一格，用網頁版（node）和 Unity 各畫一次，逐像素比較，要完全一樣。
   - 這部分是純計算，可以全自動。
2. **遊戲畫面比對**
   - 亂數換成固定種子後，同樣的按鍵輸入，兩邊跑幾秒再比畫面。
   - 用來抓碰撞、連段、傷害、怪物 AI 的差異。
3. **手感**
   - 只能靠你實際玩。每個階段結束時，請你在電腦和手機各試一次。
4. **我能自己做的**
   - 用 Unity 的 batchmode 編譯、跑測試、在背景截圖。
   - 跟現在用瀏覽器測一樣，每一步都會附截圖。

## 5. 分階段

每個階段結束都要「能玩、能比對、你確認過」才進下一階段。

| 階段 | 內容 | 完成的樣子 |
|---|---|---|
| 0 準備 | 建 Unity 專案、像素畫布、pixelfx 核心（畫筆、調色、粒子、動作）翻成 C#、比對測試工具 | 一個 pixelfx 特效在 Unity 畫出來跟網頁逐像素一樣 |
| 1 試玩片段 | 1-1 第一段：星星主角跑、跳、閃避、普攻連段、一種怪、打擊感（停頓、震動）、血條 | 你在電腦和手機上玩，手感跟網頁版一樣 |
| 2 戰鬥完整 | 5 個形態、普攻模組、技能、大招、技能樹、狀態、掉寶、背包資料 | 每個形態都能打，比對測試通過 |
| 3 關卡 | 第一章 4 關、大胃王、刺蝟、關卡機關、場景圖層、世界地圖 | 第一章從頭打到尾 |
| 4 城鎮和介面 | 碎星鎮、NPC、對話、公會、工坊、旅店、背包、技能樹、設定、標題、開場動畫 | 所有視窗都能用 |

| 6 切換 | 對照清單逐項確認跟網頁版一樣，之後新內容（第二章）改在 Unity 做 | 網頁版正式凍結或下架（待決定） |

第 4 階段的介面最花時間，第 1 階段最重要（決定手感能不能搬過去）。

## 7. 風險

- **手機效能**
  - 每格畫面用 CPU 算像素，C# 一般比瀏覽器 JS 快，但 Unity 的手機輸出要實測。
  - 第 1 階段就要在手機上量。
- **介面重做量大**
  - HTML/CSS 的版面要在 UI Toolkit 重排，像素風按鈕（ui-art.js）要重新接。
- **中文字型**
  - Unity 要自帶字型。中文字型檔很大，要裁成只含遊戲用到的字。
- **動態型別**
  - JS 物件很鬆散，C# 要把資料型別（裝備、詞綴、存檔）定清楚。
  - 這一步正好可以整理存檔格式。
- **工程很長**
  - 是很多輪對話的事。搬的途中不加新功能。
